# Secret Vault for Rust

Library provides the following crates:

- General secret value type - a simple implementation of a secure and serializable (serde and proto) type
  of any kind of secrets. Documentation is [here](secret-value/README.md).
- Secret vault - a library provides a memory-backed storage for the application secrets integrated with external source of secrets.
  Documentation is below.

## Secret Vault 

Library provides the support for the secrets coming to your application from the following sources:
 - Google Cloud Secret Manager
 - Amazon Secrets Manager
 - Azure Key Vault
 - HashiCorp Vault (KV secrets engine v2)
 - Environment variables
 - Files source (mostly designed to read K8S secrets mounted as files)
 - Temporarily available secret generator generated by cryptographic pseudo-random number generator

## Features
- Reading/caching registered secrets and their metadata in memory from defined sources;
- Memory encryption using AEAD cryptography (optional);
- Automatic refresh secrets from the sources support (optional);
- Extensible and strongly typed API to be able to implement any kind of sources;
- Memory encryption using Google/AWS KMS [envelope encryption](https://cloud.google.com/kms/docs/envelope-encryption) (optional);
- Multi-sources support;
- Snapshots for performance-critical secrets;


## Quick start

Cargo.toml:
```toml
[dependencies]
secret-vault = { version = "3.0", features=["..."] }
```
See the security consideration below about versioning.

### Available optional features for Secret Vault:

#### Cloud Provider Features
**Google Cloud Platform (GCP)**
- `gcp` - GCP support with the default TLS, same as `gcp-tls-roots`
- `gcp-secretmanager` - Google Secret Manager support with the aws-lc-rs crypto provider of gcloud-sdk
- `gcp-secretmanager-base` - Google Secret Manager support with the crypto provider your application installs
- `gcp-kms-tls-roots` (also aliased to `gcp-kms`) - Google Cloud KMS support with TLS roots and aws-lc-rs
- `gcp-kms-tls-webpki` (`gcp-kms-webpki` in 2.x, still works) - Google Cloud KMS support with WebPKI roots and aws-lc-rs
- One of the following TLS root stores is required when using GCP features:
  - `gcp-tls-roots` - System TLS roots (default)
  - `gcp-tls-webpki` - WebPKI roots

**Amazon Web Services (AWS)**
- `aws-secretmanager` - AWS Secrets Manager support
- `aws-kms-encryption` - AWS KMS envelope encryption support
- The AWS SDK always uses rustls with aws-lc-rs and the system TLS roots, so there are no TLS features for AWS

**Microsoft Azure**
- `azure-keyvault` - Azure Key Vault secrets support with the default TLS, same as `azure-keyvault-tls-aws-lc-rs`
- One of the following TLS implementations is required when using Azure features:
  - `azure-keyvault-tls-aws-lc-rs` - rustls with the aws-lc-rs crypto provider and the platform certificate verifier (default)
  - `azure-keyvault-tls-no-provider` - rustls with the crypto provider your application installs
  - `azure-keyvault-native-tls` - native TLS of the platform (OpenSSL on Linux)

**HashiCorp Vault**
- `hashicorp-vault` - HashiCorp Vault KV secrets engine v2 support with the default TLS, same as `hashicorp-vault-tls-roots` and `hashicorp-vault-tls-aws-lc-rs`
- One of the following TLS root stores is required when using HashiCorp Vault features:
  - `hashicorp-vault-tls-roots` - System TLS roots (default)
  - `hashicorp-vault-tls-webpki` - WebPKI roots
- One of the following rustls crypto providers is required when using HashiCorp Vault features:
  - `hashicorp-vault-tls-aws-lc-rs` - aws-lc-rs (default)
  - `hashicorp-vault-tls-ring` - ring

#### Encryption Features
- `ring-aead-encryption` - Encryption support using Ring AEAD
- `kms` - Base KMS support for envelope encryption

#### Utility Features
- `serde` - Serde serialization support
- `ahash` - Uses [AHashMap](https://crates.io/crates/ahash) for maps and snapshots

### Feature Flag Examples

For GCP Secret Manager with the default TLS:
```toml
secret-vault = { version = "3.0", features = ["gcp-secretmanager", "gcp"] }
```

For AWS Secrets Manager with KMS encryption:
```toml
secret-vault = { version = "3.0", features = ["aws-secretmanager", "aws-kms-encryption"] }
```

For Azure Key Vault:
```toml
secret-vault = { version = "3.0", features = ["azure-keyvault"] }
```

For Azure Key Vault with native TLS:
```toml
secret-vault = { version = "3.0", features = ["azure-keyvault-native-tls"] }
```

For HashiCorp Vault with AEAD encryption:
```toml
secret-vault = { version = "3.0", features = ["hashicorp-vault", "ring-aead-encryption"] }
```

For HashiCorp Vault with WebPKI roots and the ring crypto provider:
```toml
secret-vault = { version = "3.0", features = ["hashicorp-vault-tls-webpki", "hashicorp-vault-tls-ring"] }
```

For GCP Secret Manager with WebPKI and serde support:
```toml
secret-vault = { version = "3.0", features = ["gcp-secretmanager", "gcp-tls-webpki", "serde"] }
```

Note: Each group of TLS features above needs one feature when its source is used. The features of a group are mutually exclusive and cannot be enabled simultaneously.
`gcp`, `azure-keyvault` and `hashicorp-vault` already select the defaults, so use the TLS features instead of them, not together with them.

## Example for GCP with AEAD encryption:

```rust

// Describing secrets and marking them non-required
// since this is only example and they don't exist in your project
let secret1 = SecretVaultRef::new("test-secret1".into()).with_required(false);
let secret2 = SecretVaultRef::new("test-secret2".into())
    .with_secret_version("1".into())
    .with_required(false);

// Building the vault
let vault = SecretVaultBuilder::with_source(
    gcp::GcpSecretManagerSource::new(&config_env_var("PROJECT_ID")?).await?,
)
    .with_encryption(ring_encryption::SecretVaultRingAeadEncryption::new()?)
    .with_secret_refs(vec![&secret1, &secret2])
    .build()?;

// Load secrets from the source
vault.refresh().await?;

// Reading the secret values
let secret: Option<Secret> = vault.get_secret_by_ref(&secret1).await?;

// Or if you require it available
let secret: Secret = vault.require_secret_by_ref(&secret1).await?;
println!("Received secret: {:?}", secret);

// Using the Viewer API to share only methods able to read secrets
let vault_viewer = vault.viewer();
vault_viewer.get_secret_by_ref(&secret2).await?;

```

To run this example use with environment variables:
```
# PROJECT_ID=<your-google-project-id> cargo run --example gcloud_secret_manager_vault
```

The HTTP client of gcloud-sdk uses native-tls (OpenSSL on Linux) with `gcp-tls-roots`, and rustls with aws-lc-rs with `gcp-tls-webpki`.
With `gcp-secretmanager-base` install a rustls `CryptoProvider` at startup before creating the source, for example `rustls::crypto::ring::default_provider().install_default()`.
GCP KMS supports only aws-lc-rs, since kms-aead enables it.

## Example for Azure Key Vault

The source takes the vault URL and any credential from [azure_identity](https://crates.io/crates/azure_identity):
managed identity, Azure CLI, client secret and so on.

```rust
static SECRET_REF1: SecretVaultRef =
    SecretVaultRef::new(SecretName::from_static("db-password"));
static SECRET_REF2: SecretVaultRef = SecretVaultRef::from_key(SecretVaultKey::from_parts(
    SecretName::from_static("api-key"),
    Some(SecretVersion::from_static("4387e9f3d6e14c459867679a90fd0f79")),
    None,
));

let credential = azure_identity::ManagedIdentityCredential::new(None)?;

let vault = SecretVaultBuilder::with_source(
    azure::AzureKeyVaultSource::new("https://my-vault.vault.azure.net", credential)?,
)
    .with_encryption(ring_encryption::SecretVaultRingAeadEncryption::new()?)
    .with_secret_refs(vec![&SECRET_REF1, &SECRET_REF2])
    .build()?;
```

`SecretVersion` is the Key Vault secret version identifier; without it the latest version is read.
Key Vault secret names allow only `0-9`, `a-z`, `A-Z` and `-`, so a `SecretVaultRef` with any other
character in its name fails with `InvalidParametersError`, even when the secret is not required.
With `read_metadata` enabled, tags become labels and `expires`/`created`/`updated` become
the expiration and timestamps of `SecretMetadata`.

The TLS features select the TLS of the reqwest client the Azure SDK creates:
- `azure-keyvault-tls-aws-lc-rs` - rustls with aws-lc-rs, certificates are verified by the platform verifier;
- `azure-keyvault-tls-no-provider` - rustls with the default `CryptoProvider` of the process, so install one at startup, for example `rustls::crypto::ring::default_provider().install_default()`;
- `azure-keyvault-native-tls` - native-tls: OpenSSL on Linux and the system TLS on macOS and Windows.

Be aware that creating the source panics in reqwest when `azure-keyvault-tls-no-provider` is used without an installed `CryptoProvider`.
GCP (through gcloud-sdk) and Azure share one reqwest TLS backend in an application, and reqwest uses native-tls whenever it is enabled anywhere in the build.
So with `gcp-tls-roots` enabled, the Azure source uses native-tls whatever Azure TLS feature is selected.
`azure_identity` with its default features enables rustls in the Azure SDK, so depend on it with `default-features = false` to keep only the TLS selected here.

To run the example:
```
# VAULT_URL=https://<your-vault>.vault.azure.net cargo run --example azure_key_vault --features azure-keyvault,ring-aead-encryption
```

All examples available at [secret-vault/examples](secret-vault/examples) directory.

## HashiCorp Vault

The `hashicorp-vault` feature reads secrets from the KV secrets engine v2 through the Vault HTTP API:
- the secret name is the path of the secret inside the mount (`my-app/database`);
- the secret version is the KV v2 version number, the latest version is read when it is not specified;
- the secret value is the `data` object of the version as JSON, the same way AWS Secrets Manager returns key/value secrets;
- the JSON text is the one Vault returns: keys are sorted and `<`, `>`, `&` are escaped as `\u003c`, `\u003e`, `\u0026`, so parse it with `expose_json_value_as` and do not compare the text;
- the mount path is `secret` by default and can be changed with `with_mount`;
- the KV v2 custom metadata of the secret becomes secret labels when `read_metadata` is enabled.

```rust
static DATABASE_SECRET_REF: SecretVaultRef =
    SecretVaultRef::new(SecretName::from_static("my-app/database"));

// The options read VAULT_ADDR, VAULT_TOKEN, VAULT_NAMESPACE, VAULT_CACERT and VAULT_CLIENT_TIMEOUT from the environment
let vault = SecretVaultBuilder::with_source(hashicorp::HashiCorpVaultSource::with_options(
    hashicorp::HashiCorpVaultSourceOptions::from_env()?
        .with_mount("secret".into())
        .with_read_metadata(true),
)?)
    .with_encryption(ring_encryption::SecretVaultRingAeadEncryption::new()?)
    .with_secret_refs(vec![&DATABASE_SECRET_REF])
    .build()?;

vault.refresh().await?;

// Reading the fields of the secret with the `serde` feature enabled
let secret: Secret = vault.require_secret_by_ref(&DATABASE_SECRET_REF).await?;
let database: DatabaseConfig = secret.value.expose_json_value_as()?;
```

The environment variables are the ones the Vault CLI uses:
- `VAULT_ADDR` - the address of the Vault server, required;
- `VAULT_TOKEN` - the token sent with every request;
- `VAULT_NAMESPACE` - the Vault Enterprise namespace;
- `VAULT_CACERT` - a PEM file with CA certificates to trust in addition to the roots of the selected root store;
- `VAULT_CLIENT_TIMEOUT` - the time limit for one read, in seconds (`60`) or as a duration (`1m30s`), 60 seconds by default.

To configure the source in code use `HashiCorpVaultSourceOptions::new(address)` with `with_token`, `with_namespace`, `with_ca_certificate` and `with_timeout`.

A read that fails with 5xx or 429 from Vault (sealed, rate limited), a timeout or a connection error returns `SecretVaultError::NetworkError` and can be retried. Other failed reads return `SecretVaultError::SecretsSourceError`.

The source uses rustls, and the TLS features select its root store and crypto provider:
- `hashicorp-vault-tls-roots` - the system CA certificates;
- `hashicorp-vault-tls-webpki` - the Mozilla CA certificates from [webpki-roots](https://crates.io/crates/webpki-roots), built into the binary;
- `hashicorp-vault-tls-aws-lc-rs` or `hashicorp-vault-tls-ring` - the crypto provider.

The provider is used for the connections of the source only and is not installed as the process default.
If your application uses rustls with `ring`, enable `hashicorp-vault-tls-ring`. With both providers in one build rustls cannot choose a default one, and the application has to install it at startup.

Only token authentication is supported. For other authentication methods (AppRole, Kubernetes, cloud IAM, etc.) either log in with your own code and pass the token with `with_token`, or run Vault Agent or Vault Proxy with auto-auth and `use_auto_auth_token` and point `VAULT_ADDR` to it without a token. Be aware the source does not renew the token, so the secrets stop refreshing when it expires.

To run the example:
```
# VAULT_ADDR=http://127.0.0.1:8200 VAULT_TOKEN=<your-token> cargo run --example hashicorp_vault --features hashicorp-vault,ring-aead-encryption
```

The integration tests need a Vault server and are ignored by default. To run them with a dev server in Docker:
```
docker run -d --rm --name vault-dev -p 8200:8200 -e VAULT_DEV_ROOT_TOKEN_ID=dev-root docker.io/hashicorp/vault:latest
VAULT_ADDR=http://127.0.0.1:8200 VAULT_TOKEN=dev-root cargo test -p secret-vault --features hashicorp-vault --test hashicorp_vault_source -- --ignored
```

## Making `SecretVaultRef` available globally
It is convenient to make those references globally available inside your apps since
they do not contain any sensitive information.
References are declared as plain `static` items, no `lazy_static` or `once_cell` required
(a reference with predefined labels or a name known only at runtime still needs `std::sync::LazyLock`):

- `SecretName`, `SecretNamespace` and `SecretVersion` are created with `from_static`;
- `SecretVaultRef::new`, `with_required`, `with_auto_refresh` and `with_allow_in_snapshots` are `const`;
- a reference with a version or a namespace is created from a key with `SecretVaultKey::from_parts` and `SecretVaultRef::from_key`, since `with_secret_version` and `with_namespace` are not `const`.

```rust
use secret_vault::*;

pub static MY_SECRET_REF: SecretVaultRef =
    SecretVaultRef::new(SecretName::from_static("my-secret")).with_required(false);

pub static MY_VERSIONED_SECRET_REF: SecretVaultRef =
    SecretVaultRef::from_key(SecretVaultKey::from_parts(
        SecretName::from_static("my-versioned-secret"),
        Some(SecretVersion::from_static("1")),
        Some(SecretNamespace::from_static("aws")),
    ))
    .with_auto_refresh(true);
```

Names, namespaces and versions created with `from_static` are equal to the ones created at runtime with `.into()`,
so a static reference and a runtime one with the same key read the same secret from the vault.

## Multiple sources
The library supports reading from multiple sources simultaneously
using the concept of namespaces:

```rust

let secret_aws_namespace: SecretNamespace = "aws".into();
let secret_env_namespace: SecretNamespace = "env".into();

SecretVaultBuilder::with_source(
        MultipleSecretsSources::new()
            .add_source(&secret_env_namespace, InsecureEnvSource::new())
            .add_source(&secret_aws_namespace,
                aws::AwsSecretManagerSource::new(&config_env_var("ACCOUNT_ID")?).await?
            )
)

let secret_ref_aws = SecretVaultRef::new("test-secret-xRnpry".into()).with_namespace(secret_aws_namespace.clone());
let secret_ref_env = SecretVaultRef::new("user".into()).with_namespace(secret_env_namespace.clone());

vault.register_secrets_refs(vec![&secret_ref_aws, &secret_ref_env]).refresh().await?;

```

## Reading secret metadata from GCP/AWS/Azure secret managers
By default reading metadata (such as labels and expiration dates) from secrets is disabled
since it requires more permissions.
To enable it use options (GCP example):

```rust
// Building the vault
let vault = SecretVaultBuilder::with_source(
    gcp::GcpSecretManagerSource::with_options(
        gcp::GcpSecretManagerSourceOptions::new(config_env_var("PROJECT_ID")?)
            .with_read_metadata(true),
    )
    .await?,
)
```


## Security considerations and risks

### OSS
Open source code is created through voluntary collaboration of software developers.
The original authors license the code so that anyone can see it, modify it, and
distribute new versions of it.
You should manage all OSS using the same procedures and tools that you use for
commercial products. As always, train your employees on
cyber security best practices that can help them securely 
use and manage software products.
You should not solely rely on individuals, especially on the projects like this
reading sensitive information.

### Versioning
Please don't use broad version dependency management not to include
a new version of dependency automatically without auditing the changes.

### Protect your secrets in GCP/AWS using IAM and service accounts
Don't expose all of your secrets to the apps. 
Use IAM and different service accounts to give access only on as-needed basis.

### Zeroing, protecting memory and encryption don't provide 100% safety
There are still allocations on the protocol layers (such as the official Amazon SDK, for instance), 
there is a session secret key available in memory without KMS, etc.

So don't consider this is a completely safe solution for all possible attacks.
The mitigation some of the attacks is not possible without implementing
additional support on hardware/OS level (such as Intel SGX project, for instance).

In general, consider this as one small additional effort to mitigate some risks,
but keep in mind this is not the only solution you should rely on.

The most secure setup/config at the moment available is:
- GCP Secret Manager + KMS enveloper encryption and AEAD

because in case of GCP there are additional effort in Google Cloud SDK provided integration with this library.
One of the unexpected side-effects of not having the official SDK for Rust from Google.

## Snapshots
For performance critical secrets there are snapshots support reducing overheads from:
- encryption, so snapshots are decrypted all the time
- async runtime and possible network calls (such for KMS, etc)
- RwLock synchronization

To make secret available for snapshotting you need to enable it explicitly using `with_allow_in_snapshots` for secret refs.
For complete example look at [hashmap_snapshot.rs](secret-vault/examples/hashmap_snapshot.rs)
and verify the difference in performance below.

## Rotating application secrets strategy without downtime
This is mostly application specific area, but general idea is
to have at least two version of secrets:

- The current/latest version of secret which will be used for the new transactions/requests/data
  in your application.
- Previous version which still need to be valid to interact.

Then you have two options for configuration/version management:

- Use some configuration in your app that contains those versions and redeploy your app when you need to rotate.
  That means it will trigger refreshing all secrets at the start.
  Recommended for most of the cases, since this is more auditable and declarative.
- Updating automatically secrets and their versions using `SecretVaultAutoRefresher`
  (or your own implementation) without redeploys.
